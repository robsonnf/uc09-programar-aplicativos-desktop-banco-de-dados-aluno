Altere e remova pelo id: retirada sem perda e remoção com regra

Com o banco no servidor, várias pessoas mexem nos kits ao mesmo tempo. Três relatos chegaram: remover um Cabo apagou os Cabos de dois kits, duas retiradas simultâneas descontaram uma só, e retirar o último Notebook deu erro. Hoje você altera e remove sempre pelo id, faz a retirada numa conta só dentro do banco e decide o que acontece quando um kit com itens é removido.

A aula continua no MySQL da A08 e no mesmo repositório. Transações com vários comandos e o tratamento de falhas no meio de um lote são o tema da A10; a interface gráfica começa na A11. Use dados fictícios.

Três relatos do primeiro dia no servidor ↗

O suporte começou a usar o servidor com um script de estoque herdado, que retira e remove itens pelo nome. No primeiro dia chegaram três relatos. Remover o Cabo do kit 1 apagou também o Cabo do kit 2. Dois técnicos retiraram 1 Notebook cada, ao mesmo tempo, em máquinas diferentes: o armário ficou vazio, mas o banco mostra 1. E retirar os 2 Notebooks que restavam terminou com Check constraint 'item_chk_1' is violated.

Em dupla, antes de abrir o script, escrevam uma hipótese para cada relato. O terceiro é diferente dos outros dois: pensem se o defeito está no script ou numa regra.

Pelo id, e conferindo quantas linhas mudaram ↗

O nome de um item se repete entre kits: há um Cabo no kit 1 e outro no kit 2. Um UPDATE ou DELETE com WHERE nome = 'Cabo' atinge os dois. O id é a única coluna que aponta para uma linha só, e é por ele que o aplicativo altera e remove. O hábito da A06 continua valendo: antes de mudar, um SELECT com o mesmo WHERE mostra exatamente o que vai mudar.

Depois de um UPDATE ou DELETE, cur.rowcount diz quantas linhas o comando mudou. Zero é um aviso: o id não existe, ou a condição do WHERE não foi atendida. O repositório transforma esse zero num erro com nome, LookupError, em vez de seguir como se tivesse dado certo.

Mudou zero linhas não quer dizer que a linha não existe

O MySQL conta só as linhas que de fato mudaram. Um UPDATE que grava o mesmo valor que já estava lá encontra a linha e devolve rowcount 0, como mostra o passo 2 do tutorial (Rows matched: 1, Changed: 0). Para saber se o id existe nesse caso, faça um SELECT.

Duas retiradas ao mesmo tempo ↗

O script herdado faz a retirada em três tempos: lê o saldo, pede confirmação e grava o saldo menos a quantidade. Com uma pessoa só, funciona. Com duas ao mesmo tempo, as duas leem o mesmo saldo antes que qualquer uma grave, e a segunda gravação apaga a primeira. É a atualização perdida, e a tabela abaixo mostra o relato do Notebook passo a passo.

A correção é não levar o saldo para o Python. O UPDATE faz a conta dentro do banco, SET quantidade = quantidade - %s, e só se houver saldo, AND quantidade >= %s. O InnoDB trava a linha enquanto um UPDATE trabalha nela: o segundo espera o primeiro terminar e então faz a conta com o valor novo. Se o saldo acabou, o WHERE não é atendido, nenhuma linha muda e o rowcount 0 vira a recusa.

Ler, subtrair no Python, gravar

Entre a leitura e a gravação, outra pessoa pode ter retirado. O valor gravado já nasce velho.

cur.execute('SELECT quantidade FROM item WHERE id = %s', (item_id,))
saldo = cur.fetchall()[0][0]
cur.execute('UPDATE item SET quantidade = %s WHERE id = %s',
            (saldo - quantidade, item_id))

A conta dentro do UPDATE

O banco faz a conta com o valor do momento, e só se houver saldo. O rowcount diz se a retirada aconteceu.

cur.execute('UPDATE item SET quantidade = quantidade - %s '

Estoque zerado: a regra do banco contra a regra do objeto ↗

O terceiro relato não é defeito do script. Na A05, o ItemKit aceita retirar tudo e ficar com zero. Na A06, o banco ganhou CHECK (quantidade > 0), que fazia sentido para o cadastro, e na A08 a regra foi para o MySQL. Quando a retirada chega a zero, o banco recusa uma situação que o domínio considera normal.

A decisão desta aula separa as duas coisas: cadastrar com zero continua proibido, e quem garante é o ItemKit; estoque zerado é permitido, e o banco só recusa negativo, com CHECK (quantidade >= 0). Num banco que já tem dados, a regra muda com ALTER TABLE: apaga o CHECK antigo pelo nome e cria o novo. O nome do CHECK antigo foi dado pelo MySQL, item_chk_1; daqui em diante, dê você mesmo o nome das regras, com CONSTRAINT nome, para não precisar descobri-lo depois.

Uma migração é um arquivo, não um comando digitado uma vez

Cada máquina da turma tem um banco kits da A08. O ALTER TABLE vai num arquivo, sql/mysql/migracao_a09.sql, que qualquer um roda com SOURCE, e o esquema.sql muda junto, para que um banco novo já nasça com a regra nova.

Apagar, desativar ou levar junto ↗

Remover uma linha que outras referenciam pede uma decisão. O padrão do MySQL é recusar: apagar um kit que ainda tem itens dá o erro 1451, porque a chave estrangeira de item aponta para ele. Há outras escolhas, e cada uma tem um preço. A tabela compara as quatro, e o tutorial mostra cada uma no banco de treino.

Para o projeto, a turma fica com o padrão: um item é apagado de verdade, pelo id, e um kit com itens é recusado. O repositório traduz o erro 1451 numa exceção do domínio, KitComItens, com uma mensagem que diz o que fazer. Qualquer outro erro do banco segue como veio, como na regra de exceções da A04.

        with conexao_banco(TESTE) as con:
            cur = con.cursor()
            for script in ('esquema.sql', 'dados.sql'):
                for comando in comandos(script):
                    cur.execute(comando)

    def consultar(self, sql, valores=()):
        with conexao_banco(TESTE) as con:
            cur = con.cursor()
            cur.execute(sql, valores)
            return cur.fetchall()

    def saldo(self, item_id):
        return self.consultar('SELECT quantidade FROM item WHERE id = %s', (item_id,))[0][0]

    def test_retirar_desconta_e_devolve_o_saldo(self):

        resultados = []

        def tecnico():
            largada.wait()

import sys

from kits.banco import conexao_banco


def retirar(con, nome, quantidade, confirmar=input):
    cur = con.cursor()
    cur.execute('SELECT quantidade FROM item WHERE nome = %s', (nome,))
    saldo = cur.fetchall()[0][0]
    resposta = confirmar(f'{nome}: {saldo} em estoque. Retirar {quantidade}? (s/n) ')
    if resposta != 's':
        return saldo
    cur.execute('UPDATE item SET quantidade = %s WHERE nome = %s', (saldo - quantidade, nome))
    return saldo - quantidade


def remover(con, nome):
    cur = con.cursor()
    cur.execute('DELETE FROM item WHERE nome = %s', (nome,))


def main(argumentos):
    with conexao_banco() as con:
        if argumentos[0] == 'retirar':
            print('Novo saldo:', retirar(con, argumentos[1], int(argumentos[2])))
        elif argumentos[0] == 'remover':
            remover(con, argumentos[1])
            print('Removido.')


if __name__ == '__main__':
    main(sys.argv[1:])
