Troque para o MySQL e proteja a busca: valores sempre por parâmetro

O aplicativo dos kits sai do arquivo kits.db e passa a usar um servidor MySQL. Na mudança, um script de busca herdado quebra com um apóstrofo e mostra itens de outro kit quando alguém digita um trecho de SQL. Hoje você monta o banco no MySQL, troca o módulo de conexão e escreve inserção e consulta com parâmetros, devolvendo objetos do domínio.

A partir desta aula o banco é um MySQL 8.4 instalado em cada máquina. Atualizar e remover por identificador é tema da A09; interface gráfica e ORM ficam para depois. Use dados fictícios e senhas de treino, nunca a senha de uma conta sua.

A busca que quebra e a busca que vaza ↗

O suporte vai usar o aplicativo dos kits em várias máquinas ao mesmo tempo, e um arquivo kits.db em cada computador não serve mais: os dados passam para um servidor MySQL. Na mudança, um colega deixou pronto um script de busca de itens.

Dois relatos chegaram no primeiro dia. Buscar D'Avila no kit 1 termina com um erro de sintaxe do MySQL. E alguém que digitou ' OR 1=1 -- na busca do kit 1 viu na tela itens do kit 2. Em dupla, antes de abrir o script, escrevam uma hipótese para cada relato.

Do arquivo ao servidor ↗

No SQLite o banco é um arquivo, e quem abre o arquivo é dono de tudo. O MySQL é um servidor: um programa que fica rodando como serviço do Windows e atende conexões. Para conectar, você informa onde ele está (host e porta), quem você é (usuário e senha) e qual banco quer usar. Um mesmo servidor guarda vários bancos; nesta aula, kits para o aplicativo e kits_teste para os testes.

O SQL que você escreveu na A06 quase todo serve, mas não todo. A tabela abaixo reúne as diferenças desta aula. A mais perigosa é a da chave estrangeira: o MySQL aceita REFERENCES escrito na mesma linha da coluna, não reclama de nada e não cria a chave. Só a cláusula FOREIGN KEY (coluna) REFERENCES tabela(coluna) cria a regra.

O REFERENCES que não protege

kit_id INT NOT NULL REFERENCES kit(id) cria a tabela sem erro e sem a chave. Um item do kit 99 entra. Confira sempre com SHOW CREATE TABLE item\G: se não aparecer uma linha CONSTRAINT ... FOREIGN KEY, a regra não existe.

Senha fora do código, usuário com o mínimo ↗

O aplicativo precisa da senha do banco, mas a senha não pode estar no código: o código vai para o Git, e o Git guarda o histórico para sempre, mesmo que a linha seja apagada depois. A configuração fica em banco.ini, na raiz do projeto, listado no .gitignore. O repositório leva só banco.exemplo.ini, com a mesma forma e uma senha de mentira, para quem clonar saber o que preencher.

O aplicativo também não usa o root. O root pode apagar qualquer banco do servidor. O usuário kits_app só enxerga os bancos kits e kits_teste: se a senha dele vazar, o estrago fica limitado a eles. É o princípio do menor privilégio.

O módulo configparser, da biblioteca padrão, lê arquivos .ini. A seção [DEFAULT] vale para todas as outras; as seções [mysql] e [teste] só trocam o nome do banco. Assim o aplicativo usa kits e os testes usam kits_teste, com o mesmo usuário.

Valores por parâmetro, nunca colados no SQL ↗

Montar o comando com f-string cola o texto do usuário dentro do SQL. Um apóstrofo no texto fecha a string antes da hora e o comando vira lixo: é o erro de sintaxe do primeiro relato. Pior: um texto escrito de propósito vira parte do comando. Em ' OR 1=1 -- , o apóstrofo fecha a string, OR 1=1 torna a condição sempre verdadeira e -- transforma o resto em comentário. Isso é injeção de SQL, e é o segundo relato.

Com parâmetros, o comando e os valores viajam separados. Você escreve %s onde vai cada valor e passa os valores numa tupla. O conector prepara cada valor como dado, com as aspas e os escapes certos, e o servidor nunca o lê como comando. cur.statement mostra o que o servidor recebeu.

  • Um %s para cada valor, inclusive números. Nunca escreva '%s' com aspas: o conector já põe as aspas.
  • Os valores vão numa tupla. Com um valor só, a vírgula é obrigatória: (nome,). (1) sem vírgula é só o número 1, e o conector recusa.
  • Os curingas do LIKE vão no valor, não no comando: LIKE %s com f'%{trecho}%'.
  • Nome de tabela ou de coluna não pode ser parâmetro. Se ele variar, escolha de uma lista fixa do próprio código.

Texto colado com f-string

Quebra com apóstrofo e obedece a quem digita SQL na busca.

cur.execute(f"SELECT titulo FROM livro WHERE titulo LIKE '%{trecho}%'")

Valor por parâmetro

O apóstrofo é só um caractere; o SQL digitado vira texto procurado e não acha nada.

cur.execute('SELECT titulo FROM livro WHERE titulo LIKE %s', (f'%{trecho}%',))
Trocar ' por '' não resolve

Escapar à mão é esquecer um caso: outra aspa, uma barra invertida, um campo numérico sem aspas nenhuma. Parâmetro não é cuidado extra para casos raros: é o único jeito de passar um valor.

Linhas viram objetos, objetos viram linhas ↗

O resto do aplicativo trabalha com Kit e ItemKit, as classes da A05, e não com tuplas soltas. Um módulo de repositório faz a ponte: recebe um objeto e grava as linhas, lê as linhas e devolve objetos. O código da interface, nas próximas aulas, não vai ver SQL nenhum.

Isso também dá duas camadas de proteção. O ItemKit recusa quantidade zero antes de qualquer conexão; o CHECK do banco recusa de novo se alguém escrever direto no banco. Depois do INSERT, cur.lastrowid devolve o id que o AUTO_INCREMENT gerou, que é o identificador que a A09 vai usar para atualizar e remover.

Unread result found

Depois de um SELECT, leia as linhas com fetchall() antes de executar o próximo comando no mesmo cursor. Sem isso, o conector recusa o próximo execute com InternalError: Unread result found.

"""Testes do repositório: cada teste recria as tabelas no banco kits_teste, nunca no kits."""
import unittest
from pathlib import Path

import mysql.connector

from kits.banco import conexao_banco, ler_config
from kits.modelo import ItemKit
from kits.repositorio import buscar_itens, carregar_kit, inserir_item

RAIZ = Path(__file__).resolve().parent.parent
TESTE = ler_config('teste')


def comandos(script):
    """Os comandos de um arquivo da pasta sql/mysql, sem comentários, um por item."""
    texto = (RAIZ / 'sql' / 'mysql' / script).read_text(encoding='utf-8')
    linhas = [l for l in texto.splitlines() if not l.strip().startswith('--')]
    return [c.strip() for c in '\n'.join(linhas).split(';') if c.strip()]


class TestRepositorio(unittest.TestCase):
    def setUp(self):
        with conexao_banco(TESTE) as con:
            cur = con.cursor()
            for script in ('esquema.sql', 'dados.sql'):
                for comando in comandos(script):
                    cur.execute(comando)

    def contar_itens(self):
        with conexao_banco(TESTE) as con:
            cur = con.cursor()

def buscar_itens(con, kit_id, trecho):
    cur = con.cursor()
    sql = 'SELECT id, nome, quantidade FROM item WHERE kit_id = %s AND nome LIKE %s'
    cur.execute(sql, (kit_id, '%' + trecho + '%'))
    return cur.fetchall()
'%' + trecho + '%' concatena texto do usuário e abre brecha para injeção de SQL.

Sem ORDER BY, a ordem das linhas não é garantida, e um teste que compara listas pode falhar de vez em quando.

Um trecho com % ou _ funciona como curinga: buscar 100% traz também 1000.
