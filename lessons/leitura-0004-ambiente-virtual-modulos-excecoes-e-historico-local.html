Funciona em qualquer máquina: ambiente, módulos, exceções e o primeiro commit

O código da A03 funciona na sua máquina. Hoje ele vira um projeto que outra pessoa clona e executa: ambiente virtual, pacote com responsabilidades separadas, exceção do domínio que não esconde defeitos e o primeiro commit revisado linha por linha.

Prática com dados fictícios e biblioteca padrão, executada pelo Python do ambiente virtual. O histórico Git é local: sem remoto, push ou configuração global. O ambiente virtual isola pacotes; não é barreira de segurança. Sem banco ou interface gráfica nesta aula.

"Na minha máquina funciona" ↗

Duas situações reais de equipe: um colega clona o projeto e o programa falha porque falta um pacote que só existia na sua máquina. Outro abre a tela, digita 2 e recebe "Entrada recusada", embora 2 seja uma quantidade perfeitamente válida.

A primeira é problema de ambiente; a segunda é um except que engole qualquer erro, inclusive um erro de digitação no próprio código. Hoje você resolve as duas, e registra o resultado de forma que qualquer pessoa da equipe consiga reproduzir.

Silenciar erro não é tratar erro

Um except que captura tudo transforma defeitos do programa em mensagens para o usuário. O sistema parece funcionar, o usuário é culpado por um erro que não cometeu e o defeito fica escondido até alguém olhar o código.

Do código solto ao projeto reproduzível ↗

  1. Isolar

    Ambiente virtual por projeto, interpretador conferido na IDE e no terminal.

  2. Organizar

    Pacote com regra e apresentação separadas, testes em pasta própria.

  3. Proteger

    Exceção do domínio para entrada inválida; defeitos do código continuam aparecendo.

  4. Verificar

    Testes rodando pelo Python do ambiente, da raiz do projeto.

  5. Registrar

    Revisar o que está preparado e fazer o commit com mensagem que explica a mudança.

Ambiente virtual: o projeto leva só a receita ↗

Um ambiente virtual é uma pasta com um interpretador e os pacotes daquele projeto, separados do Python do sistema. Cada projeto tem o seu, e as versões de um não quebram o outro. A pasta .venv não vai para o repositório: vai a receita para recriá-la, o requirements.txt, mesmo que hoje ele só diga que não há dependências externas.

Chamar o Python pelo caminho explícito do ambiente dispensa ativar o ambiente e mudar a política de execução do PowerShell. A prova de que você está dentro do ambiente é o próprio processo dizer isso: sys.prefix diferente de sys.base_prefix.

Teste do clone

O projeto está reproduzível quando alguém consegue, numa pasta nova, clonar, criar o ambiente, instalar o requirements.txt e rodar os testes, só seguindo o README.

Pacote: cada arquivo com uma responsabilidade ↗

A regra do domínio fica no pacote kits; a apresentação, em app.py; os testes, em tests. Uma pasta vira pacote quando tem um __init__.py, e os imports passam a dizer de onde vem cada coisa: from kits.regras import ler_quantidade.

O bloco if __name__ == "__main__" faz a demonstração rodar só quando o arquivo é o programa principal; importar app nos testes não deve imprimir nada. E cuidado com nomes: um arquivo seu chamado json.py ou random.py encobre o módulo da biblioteca padrão para o resto do projeto.

Exceção do domínio: recusar entrada sem esconder defeito ↗

Entrada inválida é uma situação esperada: o usuário digitou "abc" ou 0. Ela merece uma exceção com nome do domínio, QuantidadeInvalida, que herda de ValueError: quem já trata ValueError continua funcionando, e quem quiser trata só a falha de quantidade.

Quando a conversão com int() falha, levante QuantidadeInvalida com raise ... from erro. A mensagem fica clara para o usuário, e o erro original continua disponível como causa para quem depura. Já NameError, TypeError e AttributeError são defeitos do programa ou uso fora do contrato: não se capturam para virar mensagem, se corrigem.

Captura tudo

Erro de digitação, Ctrl+C e entrada inválida viram a mesma mensagem; o defeito some.

try:
    quantidade = ler_quantidade(texto)
    return f"Pronta: {quantidad}"
except:
    return "Entrada recusada"

Captura só o esperado

A recusa mostra o motivo; um NameError aparece com traceback e é corrigido.

try:
    quantidade = ler_quantidade(texto)
except QuantidadeInvalida as erro:
    return f"Entrada recusada: {erro}"
return f"Pronta: {quantidade}"

O primeiro commit, revisado ↗

Um commit é uma fotografia do projeto com uma explicação. Antes de tirar a foto, confira exatamente o que entrou nela: git add com os arquivos nomeados, nunca git add . às cegas, e git diff --cached para ler o conteúdo preparado linha por linha. É nesse momento que se descobre um .env, um banco gerado ou a pasta .venv entrando sem querer.

A mensagem responde o que mudou e por quê, no imperativo e em poucas palavras: "Separa regra de quantidade em pacote kits" diz mais que "ajustes". A identidade do commit pode ser exposta numa publicação futura: configure só neste repositório, com nome e e-mail autorizados.

Comandos da revisão antes do commit
ComandoResponde
git status --shortQuais arquivos estão novos, alterados ou preparados
git add -- arquivo1 arquivo2Prepara somente o que foi nomeado
git diff --cached --statQuais arquivos vão entrar e quanto mudou
git diff --cachedO conteúdo exato que vai entrar no commit
git config --local user.nameQual identidade vai assinar o commit, só neste repositório
git log -1 --onelineO commit que acabou de ser criado

Prática: do projeto da A02 a um commit revisado ↗

Use o repositório que a dupla criou na A02. Crie as pastas kits e tests, cada uma com um __init__.py vazio, e salve cada arquivo das atividades no lugar indicado. Toda execução usa o Python do ambiente: .\.venv\Scripts\python.exe.

2. kits/regras.py: exceção do domínio

Salve em kits/regras.py. Implemente ler_quantidade: converta com int(); se a conversão falhar, levante QuantidadeInvalida com mensagem clara usando raise ... from erro; recuse zero e negativos com QuantidadeInvalida. Não capture TypeError: None está fora do contrato.

Concluído quando: "2" e " +3 " viram 2 e 3; "0", "-1", "abc" e "3.5" levantam QuantidadeInvalida; a recusa de "abc" guarda o ValueError original em __cause__; ler_quantidade(None) continua levantando TypeError.

Dica para realizar a atividade

Separe duas perguntas: o texto é um inteiro? O inteiro é maior que zero? Cada uma tem a sua mensagem.

3. tests/test_regras.py: o contrato em testes

Salve em tests/test_regras.py e escreva os testes marcados com TODO, incluindo os dois testes do app. Rode da raiz do projeto. Os testes do app devem falhar com o app.py recebido: guarde essa falha como evidência antes da atividade 4.

Concluído quando: Os testes de regras passam; os do app falham com o app.py recebido e passam depois da correção. Trocar <= 0 por < 0 na regra faz pelo menos um teste falhar.

Dica para realizar a atividade

4. app.py: o except que escondia o defeito

Salve na raiz do projeto e rode. Repare que até "2" é recusado. Troque o except genérico por except QuantidadeInvalida as erro, mostrando o motivo da recusa, e rode de novo: o defeito escondido vai aparecer com traceback. Corrija a causa. Confira que importar app não imprime nada.

Concluído quando: "2" mostra Quantidade pronta: 2; as recusas mostram o motivo; os testes do app passam; não sobra except genérico.

Dica para realizar a atividade

Leia a última linha do traceback: qual nome o Python não encontrou, e em qual linha?

"""Apresentação: mostra o resultado; a regra fica em kits.regras."""

5. Revise e registre o primeiro commit

Com tudo passando, rode git status --short, adicione os arquivos nomeados (nunca a .venv), leia git diff --cached, confira a identidade com git config --local, faça o commit com uma mensagem que explique a mudança e registre git log -1 --oneline e o status final. Sem remoto e sem push.

Concluído quando: O registro mostra o que foi preparado, a revisão do conteúdo, a mensagem, o hash curto e o status limpo, sem .venv, caches, .env ou banco no commit.
