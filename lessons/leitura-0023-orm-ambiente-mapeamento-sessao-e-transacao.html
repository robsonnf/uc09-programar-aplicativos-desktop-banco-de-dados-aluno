ORM com SQLAlchemy: tabelas como classes, sessão como transação

Até aqui, cada operação dos kits é um SQL escrito à mão. Hoje o projeto ganha um segundo jeito de falar com o mesmo banco: o SQLAlchemy 2, um ORM, que descreve as tabelas como classes Python e escreve o SQL a partir de objetos. Você instala a biblioteca, mapeia kit e item sem mudar o esquema, monta o motor a partir do banco.ini, usa a sessão como transação e refaz quatro operações do repositório com ela, provando com os mesmos critérios dos testes do SQL. O aplicativo continua usando o SQL direto: a decisão de trocar é da A25.

A aula continua no projeto da A22. Instale o SQLAlchemy 2.1.9 no .venv (pip install SQLAlchemy==2.1.9) e acrescente a linha ao requirements.txt. O esquema não muda. Use dados fictícios.

O que o ORM faz, e o que continua sendo seu ↗

Um ORM, mapeador objeto-relacional, liga linhas de tabela a objetos. Você escreve sessao.add(KitBanco(nome='Almoxarifado')) e ele escreve INSERT INTO kit; você muda item.quantidade e ele escreve o UPDATE. As consultas viram expressões Python: select(KitBanco).where(KitBanco.nome == nome). O tutorial mostra, linha por linha, o SQL que sai de cada uma.

O que o ORM não decide por você é o que a A08 à A19 ensinaram: quando a transação começa e termina, que linha precisa de trava, como a comparação do banco trata maiúsculas, o que fazer com o erro de chave estrangeira. Um repositório ORM correto mantém tudo isso; o herdado ficou mais curto porque perdeu essas decisões.

Nesta UC, o esquema continua sendo o esquema.sql. As classes descrevem as tabelas que ele cria, e o teste confere que as colunas batem. Ninguém chama create_all no projeto: assim, o SQL direto e o ORM leem e gravam as mesmas tabelas, e a turma pode comparar os dois na A25.

Mapear, ligar e abrir a sessão ↗

Cada classe herda de uma Base (DeclarativeBase), diz a tabela em __tablename__ e declara cada coluna com Mapped e o tipo do Python. As classes chamam KitBanco e ItemBanco para não confundir com o Kit e o ItemKit do domínio (A05), que têm as regras: o objeto da tabela guarda linhas, e o do domínio decide o que é válido.

O motor (Engine) sabe chegar ao banco. Ele é montado com URL.create, com cada parte do endereço no seu lugar: uma senha com @ ou dois-pontos não quebra nada, e o render_as_string(hide_password=True) mostra o endereço sem a senha. O motor guarda conexões abertas e as empresta; pool_pre_ping confere se a emprestada ainda está viva.

A sessão é o lugar onde os objetos vivem durante uma operação. Com with Session(motor) as sessao, sessao.begin(), tudo o que acontece dentro do bloco é uma transação: confirmada no fim, desfeita se algo sair errado. É o em_transacao da A10, e o kits/orm.py ganha o em_sessao, que faz isso para uma função que recebe a sessão.

As decisões que o ORM não toma ↗

Soma de itens: o SQL da A13 lê o item com FOR UPDATE. No ORM é .with_for_update() na consulta; sem ele, duas sessões leem o mesmo 3, cada uma soma 1 e as duas gravam 4. O teste com duas threads prova a trava.

Nome repetido: o WHERE nome = ... vai para o banco, e a comparação é a do MySQL (A13): treinamento redes é o mesmo kit. Comparar em Python, depois de trazer todos os kits, é mais lento e diferencia maiúsculas.

Commit: nenhuma função do repositório ORM confirma. Um sessao.commit() no meio faz a primeira metade de uma operação maior ficar, como o commit por linha da A19. flush é diferente: manda o SQL agora, para o banco dar o id ou recusar, mas a transação continua aberta.

"""Repositório ORM herdado. Para examinar: guarde o seu kits/repositorio_orm.py (copie para fora da pasta kits),
ponha este no lugar dele, rode tests.test_orm e devolva o seu."""
from sqlalchemy import delete, exc, select

from kits.modelo import Kit
from kits.orm import ItemBanco, KitBanco


def listar_kits(sessao):
    return [tuple(linha) for linha in sessao.execute(select(KitBanco.id, KitBanco.nome).order_by(KitBanco.nome, KitBanco.id))]


def criar_kit(sessao, nome):
    kit = Kit(nome)
    if any(k.nome == kit.nome for k in sessao.scalars(select(KitBanco))):
        raise ValueError(f'Já existe o kit {kit.nome}')
    novo = KitBanco(nome=kit.nome)
    sessao.add(novo)
    sessao.flush()
    return novo.id


def adicionar_item(sessao, kit_id, item):
    existente = sessao.scalar(select(ItemBanco).where(ItemBanco.kit_id == kit_id, ItemBanco.nome == item.nome))
    if existente is not None:
        existente.quantidade += item.quantidade
        sessao.commit()
        return existente.id
    novo = ItemBanco(kit_id=kit_id, nome=item.nome, quantidade=item.quantidade)
    sessao.add(novo)
    try:
        sessao.commit()
    except exc.IntegrityError as erro:
        raise LookupError(f'Kit {kit_id} não existe') from erro
    return novo.id


def remover_item(sessao, item_id):
    sessao.execute(delete(ItemBanco).where(ItemBanco.id == item_id))
