Objetos que protegem as próprias regras

Até aqui a regra de quantidade vivia em funções soltas. Hoje ela vai morar dentro de objetos: cada kit guarda seus itens, cada item protege a própria quantidade, e nada muda o estado sem passar pela regra. No caminho, você encontra um defeito clássico de estado compartilhado entre objetos.

Prática em memória com dados fictícios, no projeto e no ambiente virtual da A04. Sem banco, interface gráfica ou ORM nesta aula: a A06 transforma este modelo em tabelas. Não há nota automática.

"O cabo apareceu no kit errado" ↗

O cliente relatou: "Cadastrei 3 cabos no kit Redes e o kit Suporte, que estava vazio, passou a mostrar 3 itens." Ninguém mexeu no kit Suporte. O código tem uma classe Kit pequena, sem erro de sintaxe, e todos os testes de um kit só passam.

Antes de ver o código, em dupla: em que lugar um dado precisaria estar guardado para que dois objetos diferentes enxergassem a mesma coisa? Anotem a hipótese.

Testar um objeto só não basta

Defeitos de estado compartilhado só aparecem quando existem dois objetos. O teste que prova a independência cria dois, altera um e confere que o outro não mudou.

Do dado solto ao objeto que se defende ↗

  1. Modelar

    Decidir quais dados e comportamentos pertencem a cada objeto.

  2. Encapsular

    Validar na criação e em cada método; expor o estado só para leitura.

  3. Compor

    Montar objetos maiores a partir de objetos menores, com responsabilidades claras.

  4. Testar

    Invariantes, recusas que preservam o estado e independência entre objetos.

  5. Revisar

    Procurar estado compartilhado e herança onde deveria haver composição.

Classe, instância e self ↗

A classe descreve o que todo kit tem e faz; cada instância é um kit concreto, com o seu próprio estado. Em kit_redes.adicionar("Cabo", 3), self é o objeto kit_redes: é por ele que o método encontra a lista daquele kit, e não a de outro.

O __init__ não cria o objeto, inicializa um objeto que o Python já criou: por isso não devolve nada. E um __repr__ bem escrito, como ItemKit('Cabo', 3), faz o depurador e as mensagens de teste mostrarem o estado de verdade, em vez de um endereço de memória.

Invariantes: o objeto não aceita ficar inválido ↗

Invariante é uma regra que vale durante toda a vida do objeto: o nome nunca é vazio, a quantidade nunca é negativa. O objeto garante isso validando na criação e em cada método que altera o estado, sempre antes de alterar. Se a validação falhar depois de a quantidade já ter mudado, a recusa deixa o objeto quebrado.

Em Python não há atributo realmente privado. O sublinhado em _quantidade é uma convenção: não mexa por fora. Uma property sem setter deixa ler item.quantidade, mas obriga qualquer mudança a passar por retirar, que conhece a regra. Pelo mesmo motivo, Kit.itens devolve uma tupla: dá para ler, não dá para colocar qualquer coisa lá dentro.

Atributo aberto

Qualquer parte do sistema pode deixar o item inválido, e a regra de retirar nem é consultada.

item.quantidade = -5
kit.itens.append("qualquer coisa")

Estado protegido

Ler é livre; mudar passa pelo método que valida e preserva o estado na recusa.

@property
def quantidade(self):
    return self._quantidade

item.retirar(2)      # valida antes de subtrair
kit.adicionar("Cabo", 3)
Diga, não pergunte

Em vez de ler a quantidade, decidir fora e escrever de volta, peça ao objeto: item.retirar(2). A regra fica num lugar só e não se espalha pelas telas.

Composição: o kit tem itens ↗

Um kit tem itens; um kit não é uma lista. Quando Kit herda de list, ganha clear, sort, remove e append sem validação: qualquer código pode esvaziar o kit ou colocar um texto no lugar de um item. Guardando os itens num atributo e oferecendo só os métodos que o domínio permite, o kit decide o que pode acontecer com eles.

Herança faz sentido quando a relação é "é um" e a classe filha pode ser usada em qualquer lugar da mãe, como QuantidadeInvalida é um ValueError. Para "tem um", use composição. Os padrões de projeto que aparecem a partir da A20 (MVC, Repository) são, em grande parte, composições bem escolhidas.

Herdando de list

O kit expõe operações que o domínio não autoriza.

class Kit(list):
    ...

kit.clear()          # some com tudo
kit.append("texto")  # sem validação

Compondo com ItemKit

O kit controla a coleção e cria itens válidos.

class Kit:
    def __init__(self, nome):
        self.nome = nome
        self._itens = []

    def adicionar(self, nome, quantidade):
        item = ItemKit(nome, quantidade)
        self._itens.append(item)
        return item

Uma ferramenta revisou outra versão de ItemKit e listou os achados abaixo. Julgue cada um.

class ItemKit:
    def __init__(self, nome, quantidade):
        self.nome = nome
        self.quantidade = quantidade

    def retirar(self, q):
        self.quantidade -= q
        if self.quantidade < 0:
            raise ValueError("estoque insuficiente")
retirar altera o estado antes de validar; na recusa a quantidade já ficou negativa.

__init__ aceita nome vazio e quantidade zero, negativa ou texto.

O método deveria se chamar get_retirar para seguir a convenção do Python.
