SQL direto ou ORM: os mesmos relatórios, as mesmas provas e uma decisão registrada

O projeto tem dois jeitos de falar com o mesmo banco. Hoje os dois fazem os mesmos relatórios: situação dos itens com CASE, itens acima da média com subconsulta, kits sem itens com NOT EXISTS e o histórico de um item com UNION ALL. Um teste de contrato só cobra as duas versões. Você mede o plano da busca com EXPLAIN, cria um índice e vê o que ele resolve e o que não resolve, conhece as visões e, com essas evidências, registra a decisão do projeto num ADR: SQL direto, ORM ou os dois.

A aula continua no projeto da A24, com verificar.py terminando com código 0. O esquema ganha um índice, por uma migração. Use dados fictícios. O Guia de consultas SQL, no índice, mostra CASE, UNION, subconsultas, índices e visões no cliente mysql.

Quatro relatórios, quatro ferramentas ↗

Situação dos itens: CASE WHEN ... THEN ... ELSE ... END calcula um valor para cada linha. Ele testa as condições na ordem e para na primeira verdadeira: o zero precisa vir antes do baixo, porque 0 também é menor que 3. No ORM, case((condição, valor), ..., else_=...).

Itens acima da média: a média de todos os itens vem de uma subconsulta no WHERE, (SELECT AVG(quantidade) FROM item), calculada pelo banco. Se a subconsulta tiver um WHERE que a liga à linha de fora (kit_id = k.id), ela passa a ser a média do kit, e o relatório muda de sentido sem erro nenhum. No ORM, select(func.avg(...)).scalar_subquery().

Kits sem itens: NOT EXISTS (SELECT 1 FROM item i WHERE i.kit_id = k.id) é verdadeiro quando a subconsulta, ligada ao kit de fora, não acha nada. A A24 fez o mesmo com LEFT JOIN e IS NULL; os dois dão o mesmo resultado. No ORM, ~KitBanco.itens.any(). Com uma condição dentro do any, o sentido muda: "nenhum item com estoque" não é "nenhum item".

Histórico do item: as saídas (o item como origem) e as entradas (como destino) são duas consultas com as mesmas colunas, juntas com UNION ALL. UNION, sem ALL, tira as linhas repetidas, e duas transferências iguais no mesmo segundo são linhas repetidas. No ORM, union_all(...).subquery(), e um select dela para ordenar.

Um contrato para as duas versões ↗

Os testes dos relatórios ficam numa classe Contrato, que não herda de TestCase e só diz o resultado esperado. Duas classes de teste herdam dela e de TestCase: TestRelatoriosSql chama kits/relatorios.py com uma conexão, e TestRelatoriosOrm chama kits/relatorios_orm.py com em_sessao. O unittest roda os mesmos testes duas vezes, uma para cada versão.

O contrato é o que torna a comparação justa: as duas versões provam o mesmo, com os mesmos dados. Se uma terceira versão aparecer, ela ganha uma classe de três linhas e já está cobrada. Os dados do contrato foram escolhidos para separar os erros: um kit só com item zerado, duas transferências iguais e uma média geral diferente da média de cada kit.

O plano da consulta, índices e visões ↗

EXPLAIN mostra como o MySQL vai buscar, sem rodar a consulta. As colunas que mais importam: key, o índice escolhido; key_len, quantos bytes do índice ele usa; rows, quantas linhas ele espera ler. ANALYZE TABLE atualiza as estatísticas que o EXPLAIN usa.

A busca do adicionar_item (WHERE kit_id = ? AND nome = ? FOR UPDATE) hoje usa o índice da chave estrangeira, só pelo kit, e lê os itens do kit para achar o nome. Um índice em (kit_id, nome) acha a linha direto, e o FOR UPDATE trava menos. Já a busca da janela, com LIKE '%abo%', só aproveita o kit_id do índice: um % no começo impede usar a coluna nome. Índice serve à busca que você faz, e não a todas.

Cada índice ocupa espaço e deixa INSERT e UPDATE um pouco mais lentos, porque também precisa ser atualizado. Por isso ele entra por uma migração (A09), com o motivo escrito, e um teste confere o EXPLAIN.

Uma visão (CREATE VIEW) guarda uma consulta com nome e se consulta como uma tabela. Ela não guarda dados: cada SELECT nela roda a consulta de novo. Ajuda a dar nome a um relatório usado por várias ferramentas; no projeto, os relatórios ficam no código, onde os testes os alcançam.

Registrar a decisão: o ADR ↗

Um ADR (Architecture Decision Record) é um arquivo curto que registra uma decisão de arquitetura: o contexto, as opções, os critérios, a decisão e as consequências. Fica no repositório, em docs/decisoes/, numerado, e não é apagado quando a decisão muda: um ADR novo a substitui e diz qual.

A pergunta desta aula é do projeto, e não da ferramenta: o aplicativo dos kits continua no SQL direto, passa para o ORM ou usa os dois? Cada critério precisa de uma evidência que a turma produziu: as linhas de cada versão, o SQL gerado, as consultas por tela, os testes, a dependência nova no executável. Opinião sem evidência não entra na tabela.

"""Relatórios ORM herdados. Para examinar: guarde o seu kits/relatorios_orm.py (copie para fora da pasta kits),
ponha este no lugar dele, rode tests.test_relatorios e devolva o seu."""
from sqlalchemy import case, func, literal, select, union

from kits.orm import ItemBanco, KitBanco, MovimentacaoBanco
from kits.relatorios import LIMITE_BAIXO


def situacao_itens(sessao):
    situacao = case((ItemBanco.quantidade < LIMITE_BAIXO, 'baixo'), (ItemBanco.quantidade == 0, 'esgotado'), else_='ok')
    consulta = (select(KitBanco.nome, ItemBanco.nome, ItemBanco.quantidade, situacao).join(ItemBanco.kit)
                .order_by(KitBanco.nome, ItemBanco.nome, ItemBanco.id))
    return [tuple(linha) for linha in sessao.execute(consulta)]


def itens_acima_da_media(sessao):
    media = select(func.avg(ItemBanco.quantidade)).where(ItemBanco.kit_id == KitBanco.id).scalar_subquery()
    consulta = (select(KitBanco.nome, ItemBanco.nome, ItemBanco.quantidade).join(ItemBanco.kit)
                .where(ItemBanco.quantidade > media).order_by(ItemBanco.quantidade.desc(), KitBanco.nome, ItemBanco.nome))
    return [tuple(linha) for linha in sessao.execute(consulta)]


def kits_sem_itens(sessao):

def movimentos_do_item(sessao, item_id):
    saidas = select(MovimentacaoBanco.momento, literal('saída').label('tipo'), MovimentacaoBanco.quantidade,
                    MovimentacaoBanco.destino_id.label('outro')).where(MovimentacaoBanco.origem_id == item_id)
    entradas = select(MovimentacaoBanco.momento, literal('entrada').label('tipo'), MovimentacaoBanco.quantidade,
                      MovimentacaoBanco.origem_id.label('outro')).where(MovimentacaoBanco.destino_id == item_id)
    todos = union(saidas, entradas).subquery()
    consulta = select(todos).order_by(todos.c.momento, todos.c.tipo, todos.c.outro)
    return [tuple(linha) for linha in sessao.execute(consulta)]
