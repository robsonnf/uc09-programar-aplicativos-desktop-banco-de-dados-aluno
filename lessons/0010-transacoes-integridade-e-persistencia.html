Transfira com tudo ou nada: transação, travas e o que fica gravado

Mover unidades de um kit para outro são três comandos: tirar da origem, pôr no destino e anotar no histórico. Se só parte deles ficar gravada, um Cabo some ou aparece do nada. Hoje você junta os três numa transação no MySQL, trava o que vai ler para decidir, trata o deadlock tentando de novo e confere o que sobrevive quando o servidor reinicia.

A aula continua no MySQL da A08 e no mesmo repositório, com a retirada e a remoção da A09. Transações com centenas de linhas, como a importação de um arquivo, voltam na A23; a interface gráfica começa na A11. Use dados fictícios.

Vários comandos que valem juntos ↗

  1. Abrir

    Começar a transação: no Python o conector já abre; no cliente mysql, START TRANSACTION.

  2. Travar o que decide

    Ler com SELECT ... FOR UPDATE a linha cujo valor decide o que fazer.

  3. Fazer os passos

    Tirar da origem, pôr no destino, anotar no histórico, sem commit no meio.

  4. Fechar

    Sem erro, commit. Com erro, rollback de tudo, e o erro segue.

  5. Tentar de novo

    Se o banco escolher a transação como vítima de deadlock, rodar a transação inteira outra vez.

  6. Provar

    Testar o erro no meio, duas pessoas ao mesmo tempo e o servidor reiniciando.

Três comandos, uma transação ↗

Na A07, no SQLite, o tudo ou nada era um lote de INSERT. Agora os comandos são diferentes entre si: um UPDATE na origem, um UPDATE ou INSERT no destino e um INSERT no histórico. Se o segundo falhar e o primeiro ficar, a unidade some; se o terceiro faltar, a unidade muda de lugar sem deixar rastro.

No Python, o conector do MySQL começa com o autocommit desligado: o primeiro comando abre uma transação, e tudo fica pendente até o commit ou o rollback, como no sqlite3. O conexao_banco da A08 já faz isso: sem erro, commit; com erro, rollback e o erro segue. O que muda nesta aula é onde ficam os comandos: todos dentro do mesmo bloco, e nenhum commit no meio.

Um erro de um comando não desfaz a transação. O MySQL recusa só aquele comando, e os anteriores continuam pendentes, esperando o seu commit ou rollback. O exemplo mostra isso: depois da recusa, a própria transação ainda vê o saldo descontado.

No cliente mysql é ao contrário

O cliente mysql começa com autocommit ligado: cada comando é gravado na hora. Para juntar comandos numa transação no cliente, abra com START TRANSACTION e feche com COMMIT ou ROLLBACK, como no tutorial.

O que uma transação enxerga das outras ↗

Enquanto uma transação está aberta, outras conexões continuam gravando. O nível de isolamento padrão do MySQL, REPEATABLE READ, faz uma promessa: dentro da transação, o mesmo SELECT devolve sempre a mesma coisa, como uma foto tirada na primeira leitura. Os passos 4 a 6 do tutorial mostram a foto: outra conexão grava 5, e a transação continua lendo 2.

A foto é boa para um relatório, que precisa de números coerentes entre si. Para decidir uma escrita, é perigosa: você conferiria o saldo numa foto velha. A leitura com FOR UPDATE não usa a foto. Ela lê o valor mais recente e trava a linha até o fim da transação, e quem quiser mudar a linha espera. É assim que a transferência confere o saldo da origem antes de descontar.

Dois níveis de isolamento do MySQL
NívelUm SELECT comum dentro da transação vêQuando aparece
REPEATABLE READ (padrão)A foto da primeira leitura: o mesmo valor do começo ao fim.É o que o kits usa, sem configurar nada.
READ COMMITTEDO último valor que recebeu commit, a cada SELECT.Comum em outros bancos, como o PostgreSQL; no MySQL, só se alguém mudar a configuração.

Conferir com um SELECT comum

Outra transação pode descontar entre a sua leitura e o seu UPDATE: você decide com um saldo que já mudou.

cur.execute('SELECT quantidade FROM item WHERE id = %s', (item_id,))

Conferir travando

Lê o valor mais recente e segura a linha até o commit ou o rollback.

cur.execute('SELECT quantidade FROM item WHERE id = %s FOR UPDATE', (item_id,))

Espera, desistência e deadlock ↗

Quem pede uma linha travada espera. Se a espera passa de innodb_lock_wait_timeout, 50 segundos por padrão, o comando desiste com o erro 1205. É sinal de uma transação que ficou aberta tempo demais, como um terminal esquecido com START TRANSACTION.

O deadlock é diferente: duas transações esperam uma pela outra, e nenhuma espera resolveria. Transferir um Cabo do kit 1 para o kit 2 trava o item 1 e depois o item 3. Ao mesmo tempo, transferir um Cabo do kit 2 para o kit 1 trava o item 3 e depois o item 1. O MySQL percebe o ciclo na hora, escolhe uma vítima, desfaz a transação inteira dela e devolve o erro 1213. A outra segue.

A vítima não fez nada errado. A resposta certa é rodar a transação inteira de novo, numa conexão nova, porque o banco já desfez tudo o que ela tinha feito. Repetir só o comando que falhou é pior do que desistir: o destino receberia a unidade sem a origem ter perdido nada. Três tentativas no total bastam na prática, mesmo com a máquina ocupada; se a terceira também for vítima, o erro segue para quem chamou.

TempoTécnico 1: kit 1 para kit 2Técnico 2: kit 2 para kit 1

Repetir o comando que falhou

O banco já desfez o desconto da origem. Repetir só o último passo cria uma unidade do nada.

try:
    cur.execute(somar_no_destino, valores)
except mysql.connector.Error as erro:
    if erro.errno == 1213:
        cur.execute(somar_no_destino, valores)

Repetir a transação inteira

Uma conexão nova, todos os passos de novo, e um limite de tentativas.

for tentativa in (1, 2, 3):
    try:
        with conexao_banco() as con:
            return operacao(con)
    except mysql.connector.Error as erro:
        if erro.errno != 1213 or tentativa == 3:
            raise

O que fica gravado ↗

Commit é a promessa de persistência: depois dele, a mudança sobrevive a desligar o cliente, a queda da rede e a reiniciar o servidor. O que estava pendente, sem commit, some. Os passos 14 a 16 do tutorial reiniciam o serviço com uma transação aberta e mostram as duas coisas.

Há comandos que fazem commit sem você pedir. CREATE TABLE, ALTER TABLE e DROP TABLE, os comandos que mudam a estrutura, gravam o que estava pendente antes de rodar, mesmo um CREATE TABLE IF NOT EXISTS que não cria nada. Depois deles, o ROLLBACK não tem mais o que desfazer. Por isso a estrutura muda em migrações, rodadas sozinhas, e nunca no meio de uma operação do aplicativo.

O rollback desfaz as linhas, mas não devolve os números do AUTO_INCREMENT. Um INSERT recusado ou desfeito gasta o id que receberia, e o próximo item pula um número. Ids servem para identificar, não para contar: nunca conte com ids sem buracos.

"""Script herdado: transfere unidades de um item para outro kit e anota no histórico.

Uso: python transferir.py ITEM_ID KIT_DESTINO QUANTIDADE
Relatos do suporte:
- transferir 1 Cabo do item 1 para o kit 9, que não existe, mostrou Falhou, mas o kit 1 ficou com um Cabo a menos;
- duas pessoas trocando Cabos entre os kits 1 e 2 ao mesmo tempo: algumas transferências mostraram Falhou
  com Deadlock found, e a contagem de Cabos não fechou no fim do dia.
"""
import sys

import mysql.connector

from kits.banco import conexao_banco
from kits.repositorio import retirar


def transferir(con, item_id, kit_destino, quantidade):
    cur = con.cursor()
    retirar(con, item_id, quantidade)
    cur.execute('CREATE TABLE IF NOT EXISTS movimentacao ('
                'id INT AUTO_INCREMENT PRIMARY KEY, origem_id INT NOT NULL, destino_id INT NOT NULL, '
                'quantidade INT NOT NULL, momento TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP)')
    cur.execute('SELECT nome FROM item WHERE id = %s', (item_id,))
    nome = cur.fetchall()[0][0]
    cur.execute('UPDATE item SET quantidade = quantidade + %s WHERE kit_id = %s AND nome = %s',
                (quantidade, kit_destino, nome))
    if cur.rowcount == 0:
        cur.execute('INSERT INTO item (kit_id, nome, quantidade) VALUES (%s, %s, %s)',
                    (kit_destino, nome, quantidade))
        destino_id = cur.lastrowid
    else:
        cur.execute('SELECT id FROM item WHERE kit_id = %s AND nome = %s', (kit_destino, nome))
        destino_id = cur.fetchall()[0][0]
    cur.execute('INSERT INTO movimentacao (origem_id, destino_id, quantidade) VALUES (%s, %s, %s)',
                (item_id, destino_id, quantidade))


def main(argumentos):
    with conexao_banco() as con:
        try:
            transferir(con, int(argumentos[0]), int(argumentos[1]), int(argumentos[2]))
            print('Transferido.')
        except mysql.connector.Error as erro:
            print('Falhou:', erro)


if __name__ == '__main__':
    main(sys.argv[1:])
